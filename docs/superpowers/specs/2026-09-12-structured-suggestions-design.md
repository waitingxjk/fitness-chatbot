# Structured exercise suggestions

Approved in conversation on 2026-09-12. A suggestion is either a single exercise, alternatives (choose one), or an ordered session (perform all). Each exercise uses its active catalog ID, localized details and an explicit `set_prescriptions` array. A set contains `kind` (warmup/working), repetitions XOR duration_seconds, load (strategy/value/unit/convention/explanation), target_rir_min/max and rest_seconds. Unknown load remains null/trial; no completed records are created by accepting a suggestion.

Single cards expose details, set editing and add-to-current only when a current workout exists; iOS validates the actual current workout and creates incomplete drafts idempotently. Session cards show theme/time, ordered exercises, expandable/editable sets, replacement via re-planning, and whole-plan confirmation. Acceptance saves an immutable chosen version. Flutter presents accepted plans as pending, starts only on explicit Start, initializes incomplete sets in order atomically, and retains pending plans if another workout is active. Web acceptance must never claim that a local workout was created.

Compatibility: existing item-level sets/repetitions/duration/rest fields remain summaries for old clients and old stored plans; consumers expand these only when set_prescriptions is absent. Explicit per-set data is authoritative. Search cards have no invented prescription. Alternatives never implicitly form a session. Exercise cards gain `set_prescriptions`; session items gain the same field. Chat responses gain `suggestion_kind`: single_exercise, alternatives, session_plan or null.

Server plan API remains GET /v1/training/plans and GET /plans/{id}; accepted event remains POST /plans/{id}/events with event_id/expected_revision/kind. Add POST /plans/{id}/revision for user edits: {revision_id UUID, expected_revision, items:[{exercise_id,set_prescriptions}]}. This creates a new proposed child version with validated user-entered loads, dose-type compatibility and recomputed totals, preserving original. Repeating revision_id with identical contents returns the same result; conflicting contents or stale revision fails. No server endpoint writes workout snapshots except existing iOS sync.

Validation: real catalog references, per-set units/types/ranges, time from every set and rests, immutable versions, stale-write and duplicate protection, saved-history display, account isolation, and legacy fallback. Automated tests use synthetic models only. Verify browser desktop/mobile visuals and Flutter pending/start/append tests. Preserve unrelated edits and canonical OpenPencil file.
